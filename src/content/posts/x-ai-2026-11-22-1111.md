## AI 热点
1. **Lean and Mathlib communities certify Alpöge’s 17M-line Lean proof of the Riemann Hypothesis**: a joint statement endorsed by the Lean FRO and the Mathlib Initiative says “we have full confidence that Alpöge's proof of the Riemann Hypothesis is correct.” Within a day dozens of people reproduced the same raw proof export; a community file that imports only Mathlib isolates the RH statement, and two independent tools (comparator and con-leche --compare) confirmed the library proves exactly Mathlib’s `RiemannHypothesis`. The export was checked by Lean’s kernel plus the con-leche and con-ron checkers—which come with a formal proof, relative to set theory, that they cannot accept a false proof—and several third-party checkers in other languages, all run on an inert export out of reach of any malicious proof code. HN thread passed 870 points; the MIT verification-file page is at math.mit.edu/~drew/grh/. https://leanprover-community.github.io/blog/posts/riemann-hypothesis/ [HN](https://news.ycombinator.com/item?id=50589618) [rohanpaul](https://x.com/rohanpaul_ai/status/2124187865899049164)
> [zh] **Lean 与 Mathlib 社区认证 Alpöge 的 1700 万行 Lean 黎曼猜想证明**：由 Lean FRO 和 Mathlib Initiative 背书的联合声明称「我们完全确信 Alpöge 的黎曼猜想证明是正确的」。一天之内数十人复现出同一份原始证明导出文件；社区另加了一个只导入 Mathlib 的文件单独隔离黎曼猜想的陈述，并用 comparator 和 con-leche --compare 两个独立工具确认该库证明的正是 Mathlib 的 `RiemannHypothesis`。导出文件经 Lean 官方内核、con-leche 与 con-ron 检查器（附有相对集合论的形式化证明，保证不会接受错误证明）以及多个用其他语言实现的第三方检查器验证，且都在与证明源码隔离的惰性导出上运行，防止恶意代码干扰。HN 讨论超过 870 分；MIT 的验证文件页面在 math.mit.edu/~drew/grh/。
2. **NVIDIA’s CPU-ARC caches an LLM’s reasoning as CPU-executable code, 16–291x cheaper to reuse**: the paper argues LLMs “re-invent the wheel all the time,” re-solving problems from scratch even when only wording or numbers change. Claude Opus 4.5 turns a reasoning trace into “semantic functions”—Python callables whose inputs and callees are referenced by natural-language descriptions—that run on CPU, calling a fine-tuned Llama 3.2 1B only for small text jobs. Caches matched or beat the source model (AIME ’25: 93.3% vs 83.3%), passed 90%+ of phrasal, parametric and combined rewrites, and cost $0.0004 per AIME sample; building costs 12–84x one source call, so an AIME cache pays off after about 13 reuses. Rohan Paul’s takeaway: if an agent runs the same prompt on new inputs all day, cache the reasoning as code and call the LLM only on misses. https://arxiv.org/abs/2611.09891 [rohanpaul](https://x.com/rohanpaul_ai/status/2124177125247013266)
> [zh] **英伟达 CPU-ARC：把 LLM 的推理缓存成可在 CPU 上执行的代码，复用成本降 16–291 倍**：论文指出 LLM 总在「重新发明轮子」，即使只改了措辞或数字也要从头再解一遍。方法是让 Claude Opus 4.5 把推理过程改写成「语义函数」——输入和被调函数都用自然语言描述来引用的 Python 函数——在 CPU 上执行，只有提取数值这类小文本活才调用微调过的 Llama 3.2 1B。缓存准确率持平或超过源模型（AIME ’25 为 93.3% 对 83.3%），对改写措辞、改参数及两者叠加的变体通过率都在 90% 以上，每道 AIME 题调用成本 0.0004 美元；构建成本是单次源模型调用的 12–84 倍，AIME 缓存大约复用 13 次即回本。Rohan Paul 的建议：如果你的 Agent 整天拿同一套提示词处理新数据，就把推理缓存成代码，只在未命中时再调 LLM。

## 有趣用法和干货
1. **Harrison Chase: “How to build a knowledge factory”**: the missing piece for company AI is “not better models, it’s not just more context - it’s better knowledge.” Keep three kinds—skills (how to do the work), domain knowledge (how the business works) and data-access guidance (which source holds what and how to query it)—and don’t maintain them by hand: give working agents a tool to flag missing or wrong knowledge, and run a background curator agent on a cadence that reads raw sources (Notion, Slack), agent traces and those flags to update the knowledge; storage (GitHub skills, Notion, LangSmith Context Hub, Neo4j) matters least. LangChain’s internal GTM and content agents and LangSmith Engine run this way; advice: start with one recurring workflow and close the loop. 4.8k bookmarks. https://www.langchain.com/blog/knowledge-factory [X](https://x.com/hwchase17/status/2124181216719151585)
> [zh] **Harrison Chase：《如何建一座知识工厂》**：让 AI 在公司里真正起作用，缺的「不是更好的模型，也不只是更多上下文，而是更好的知识」。要维护三类知识：技能（怎么做事）、领域知识（业务怎么运转）、数据访问指南（什么数据在哪、怎么查）；不要手工维护：给干活的 Agent 一个工具来标记缺失或错误的知识，再让一个后台「策展 Agent」定期读取原始资料（Notion、Slack）、Agent 运行轨迹和这些标记来更新知识；存储形式（GitHub 技能、Notion、LangSmith Context Hub、Neo4j）反而最不重要。LangChain 内部的 GTM、内容 Agent 和 LangSmith Engine 都这样运行；建议从一个重复性工作流开始把闭环跑通。收藏 4.8k。
2. **OpenAI’s GPT-6.2 prompt templates for writing and initiative**: beyond the coding rules, the “Using GPT-6.2” docs note Astra writes more briefly by default, so “be concise” instructions deserve a second look, and give a template making the final answer “fully self-contained,” written anew for the reader without carrying over shorthand from reasoning, tool calls or subagent instructions. Another tells the model not to end a turn on a suggested next step it is authorized to take, pausing only for a major scope change, a real blocker, a user decision, or irreversible or destructive actions—otherwise make reversible assumptions, flag them and keep going. The Decoder adds that editing earlier conversation history in the API discards prior reasoning, and that temperature and top_p are gone. https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6.2-astra [The Decoder](https://the-decoder.com/openai-shares-new-prompting-tips-for-gpt-6-2-astra-and-sol-to-fix-brief-answers-and-unnecessary-questions/)
> [zh] **OpenAI 的 GPT-6.2 写作与主动性提示词模板**：除了编码规则，《Using GPT-6.2》文档还指出 Astra 默认写得更短，因此「请简洁」这类指令值得重新审视；并给出一个模板，要求最终答复「完全自成一体」，为读者重新写，不沿用推理、工具调用或给子 Agent 指令里的简写。另一个模板让模型在有权执行时不要以「建议下一步」结束回合，只在任务范围大变、真正受阻、需用户决定或不可逆/破坏性操作时才停下——其余情况做可回退的假设、标明后继续干。The Decoder 补充：在 API 里改动早先的对话历史会丢弃之前的推理内容，temperature 和 top_p 参数也已取消。
3. **Matt Pocock: teach an agent your writing style with a swipe-style scorer**: build a small app where the agent sends you example sentences one at a time to score 1–4 or pick the better of two; then plan an article together and write it sentence by sentence, letting the agent test its own hypotheses about your style and build a profile over time. 1.3k likes and 1.3k bookmarks. https://x.com/mattpocockuk/status/2124214098984370645
> [zh] **Matt Pocock：用「左右滑」评分器教 Agent 学你的文风**：做一个小应用，让 Agent 一次发一句示例句给你打 1–4 分，或从两句里选更好的一句；然后和它一起规划文章、逐句写作，让 Agent 自己验证关于你文风的假设，逐步积累出风格档案。1.3k 赞、1.3k 收藏。
