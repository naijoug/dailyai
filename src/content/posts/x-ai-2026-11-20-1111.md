## 有趣用法和干货
1. **OpenAI’s Performance Factory: Codex agents find, fix and verify ChatGPT slowdowns**: OpenAI describes how its performance work moved from manual investigations to Codex as a partner, then to a shared `perf-forensics` skill that tells Codex which of 30+ in-house performance tools to use and how to work a slowdown (when it began, which requests are affected, whether a deploy or config change explains it), and finally to agent workflows: a performance alert opens a task, an agent investigates and records findings and proposes a fix for an engineer to review, and after deployment another agent picks up the same task to confirm latency is back to baseline. In just over three months the Regression Workflow ran 1,700+ investigations and root-caused 600+ cases, about 17 a day; the current bottleneck is engineers reviewing and merging fixes. https://x.com/OpenAIDevs/status/2123471880292299171 [OpenAI 博客](https://openai.com/index/how-openai-performance-factory-keeps-chatgpt-fast/)
> [zh] **OpenAI 的 Performance Factory：用 Codex Agent 找出、修复并验证 ChatGPT 变慢问题**：OpenAI 讲了性能工作的演进：先是人工排查，再把 Codex 当搭档，然后把性能团队的排查流程写成共享 skill `perf-forensics`，告诉 Codex 何时用 30 多个内部性能工具中的哪一个、如何拆解一次变慢（何时开始、影响哪些请求、能否用部署或配置变更解释），最后做成 Agent 工作流：性能告警触发后开任务，一个 Agent 调查并记录发现、提出修复交工程师审核，上线后另一个 Agent 接手同一任务，确认延迟回到基线。三个多月里 Regression Workflow 跑了 1700 多次调查、定位了 600 多个根因，约每天 17 次；现在的瓶颈是工程师审核和合并修复。
2. **GPT-6.2 agents: keep the prefix unchanged or the Responses API drops your reasoning**: starting with GPT-6.2, each reasoning item is tied to the history before it, so editing earlier messages makes the API drop the reasoning that follows, costing tokens, latency and possibly quality. OpenAI’s new guide lists the append-only alternatives: append a `configuration_update` item instead of changing `reasoning.effort` or `text.format`; add tools with an `additional_tools` item or restrict them with `allowed_tools` instead of editing `tools`; append a new developer message rather than rewriting the first one; and if you use custom compaction, put the compacted item at the end of context (OpenAI’s own compaction keeps later reasoning). The new `input_transformations` field and a “Reasoning removals” section in the Usage dashboard show what was dropped and why. https://x.com/OpenAIDevs/status/2123566018866151579 [指南](https://developers.openai.com/api/docs/guides/keep-prefix-unchanged)
> [zh] **GPT-6.2 Agent：别改前缀，否则 Responses API 会丢掉推理**：从 GPT-6.2 起，每个推理项都绑定在它之前的对话历史上，一旦修改早先的消息，API 会丢弃其后的推理，带来额外 token、延迟，还可能降低质量。OpenAI 新指南给出只追加的替代做法：不要改 `reasoning.effort` 或 `text.format`，而是追加 `configuration_update` 项；加工具用 `additional_tools` 项、限制工具用 `allowed_tools`，不要改 `tools`；更新指令就追加新的 developer 消息，不要改第一条；自研压缩要把压缩结果放在上下文末尾（OpenAI 自家压缩会保留后续推理）。新的 `input_transformations` 字段和用量面板里的「Reasoning removals」可以查看丢了什么、为什么丢。
3. **Google’s GUARD: self-improving agent harnesses that don’t regress**: with the base model frozen, agents keep editing their prompts, skills, tool rules and memory, but without an external grader those self-edits often break things that already worked, forget skills and bloat memory. GUARD splits each task into pre-execution self-checks, grades trajectories against them, pins rules already mastered while prioritizing newly broken behaviors, picks among parallel candidate edits by group-relative fitness, and a “Soft-HURT” gate only promotes an edit when gains outweigh regressions; at test time one frozen harness runs in a single pass, with less deployment token usage. omarsar0’s “bookmark it” post drew about 300 bookmarks. https://x.com/omarsar0/status/2123420538030957015 [arXiv](https://arxiv.org/abs/2611.23476)
> [zh] **谷歌 GUARD：不倒退的自我改进 Agent 外壳**：底座模型冻结、Agent 不断改自己的提示词、技能、工具规则和记忆，但没有外部评分时，这种自我修改常常把原本好用的东西改坏、遗忘技能、让记忆膨胀。GUARD 把每个任务拆成执行前的自检项，用它们给轨迹打分，固定已掌握的规则、优先处理新被改坏的行为，在多个并行候选修改里按组内相对适应度挑选，再由「Soft-HURT」闸门只放行收益大于退化的修改；测试时一个冻结的外壳单次运行，部署 token 更少。omarsar0 那条「建议收藏」的帖子约 300 收藏。
4. **Bruce Van：五句用了很久的简单提示词**：防吹捧用「基于批判与自我批判的理论武器，给我一个更好的版本」；审代码用「盲审一下未提交的代码，按模块审查。按严重程度列问题，写清文件、行号、原因和改法」；重构用「对 xx 模块做消融实验」，逐个去掉或替换部分，看哪些才是核心；状态切换总出 bug 时让它「找到我应用中所有的隐式状态机」，列出状态、触发事件和易错边界；不知道怎么办时让它「按照最佳实践」，先讲业内通常怎么做、为什么，再结合自身情况给步骤。https://x.com/bruc3van/status/2123573034816786725
> [en] **Bruce Van: five simple prompts he has relied on for a long time**: to stop flattery, “using the theoretical weapon of criticism and self-criticism, give me a better version”; for review, “blind-review the uncommitted code module by module, list issues by severity with file, line, reason and fix”; for refactoring, “run an ablation on module xx,” removing or swapping parts to see what is core; for recurring state bugs, “find every implicit state machine in my app,” listing states, triggering events and error-prone edges; and when stuck, “follow best practice,” first explaining what the industry usually does and why, then giving concrete steps for your case.
