## AI 热点
1. **OpenAI’s chief scientist publishes internal perplexity numbers and proposes industry “common limits”**: in “Perplexity and Intelligence,” Jakub Pachocki argues perplexity (cross-entropy loss) should be the shared yardstick for comparing labs and setting safety standards, and discloses OpenAI’s curve on a held-out set drawn from its own codebase: GPT‑3.5 at a log-perplexity of ~0.99, GPT‑4 at ~0.91, today’s models below 0.8, and a ~0.76 model that began producing groundbreaking math results. He expects new transformative capabilities in the ~0.68–0.7 window, says an avalanche of pretraining advances could come “as soon as 2027,” and proposes limits developers commit not to cross until monitoring hits a concrete milestone such as a successor to CoT monitors; the post itself flags weak points (datasets differ across labs, chain-of-thought gains don’t lower perplexity, the floor is unknown). Sam Altman called it “the most important thing OpenAI has published in awhile” (8.2k likes) and Greg Brockman and Noam Brown backed it, while Nathan Lambert said it “squashes intelligence a bit too much into one quantity.” https://openai.com/index/perplexity-and-intelligence/ https://x.com/sama/status/2124551594691932405 https://x.com/natolambert/status/2124660436905926981
> [zh] **OpenAI 首席科学家公开内部困惑度数据，提议设定行业「共同上限」**：Jakub Pachocki 在《Perplexity and Intelligence》中主张用困惑度（交叉熵损失）作为各家实验室横向比较和制定安全标准的共同尺度，并公开了 OpenAI 在一个取自自家代码库的留出数据集上的曲线：GPT‑3.5 的对数困惑度约 0.99，GPT‑4 约 0.91，如今的模型已低于 0.8，而约 0.76 的模型开始做出突破性的数学成果。他预计在约 0.68–0.7 区间会出现新的颠覆性能力，「最早 2027 年」可能迎来预训练突破的雪崩，并提议各家承诺在监控能力达到具体里程碑（如 CoT 监控的继任方案）之前不越过上限；文中也列出了短板（各家数据集不同、思维链带来的提升不降低困惑度、下限未知）。Sam Altman 称这是「OpenAI 很久以来发布的最重要的东西」（8.2k 赞），Greg Brockman 和 Noam Brown 表态支持，Nathan Lambert 则认为它「把智能过度压缩成了一个数」。

5. **BuggyMLE: harder ML-engineering benchmarks by having agents inject bugs**: Elvis Saravia highlights a Google paper in which agents inject controlled bugs into 222 working ML repositories; a Code Complexity Index built from ten repo features predicts average solve rates across eight coding benchmarks with R² = 0.951, and on a graded MLE-Bench Lite the best of 14 models falls from a 95% solve rate on the easiest tier to 9% on the hardest. A Qwen3.5-9B trained on the bug curriculum rivals frontier models there and lifts SWE-bench Lite from 24% to 33%; patch size and code complexity are the strongest difficulty predictors. https://x.com/omarsar0/status/2124584960464220408 https://arxiv.org/abs/2611.25088
> [zh] **BuggyMLE：让 Agent 往代码里注入 bug，造出更难的机器学习工程基准**：Elvis Saravia 推荐了一篇谷歌论文：Agent 向 222 个可运行的机器学习仓库注入受控 bug；由十项仓库特征构成的代码复杂度指数，能以 R² = 0.951 预测八个编程基准上的平均解题率；在分级版 MLE-Bench Lite 上，14 个模型中最强者在最简单一档解出 95%，最难一档只有 9%。用这套 bug 课程训练的 Qwen3.5-9B 在该基准上可比肩前沿模型，并把 SWE-bench Lite 从 24% 提到 33%；补丁大小和代码复杂度是难度的最强预测因素。

## 有趣用法和干货
1. **Vox: paste one cleanup prompt into your messiest project every time a new model drops**: “Read this entire project and find everything that's broken, inconsistent, inefficient, or no longer needed. Prefer deleting over simplifying, simplifying over optimizing, and optimizing over automating. Run my app, open every page in Chrome yourself and screenshot it. List the 5 biggest hierarchy and density problems first. Fix what you're sure about and list the rest for me to review.” Meant for Claude Code or Codex; 2.5k likes and 4.6k bookmarks. https://x.com/Voxyz_ai/status/2124548469540974596
> [zh] **Vox：每出一个新模型，就把这段清理提示词贴进你最乱的项目**：「通读整个项目，找出所有坏掉的、不一致的、低效的或已经不需要的东西。删除优先于简化，简化优先于优化，优化优先于自动化。运行我的应用，自己用 Chrome 打开每个页面并截图。先列出层级和信息密度上最大的 5 个问题。有把握的直接修，其余列出来给我审。」适用于 Claude Code 或 Codex；2.5k 赞、4.6k 收藏。
2. **宝玉：Agent 说「验证完了」，怎么才能真的信它**：五条经验——一、别依赖对抗式验证，多个 Agent 互相挑刺缺统一验收标准，常常越改越偏；二、先给清晰的验收标准和能自验的环境，比如「完成后截图对比设计稿，像素一个都不要差」，它就会自己写对比工具返工；三、越早验证返工越便宜，先做可行性分析、原型和技术方案文档；四、让 Agent 交截图、录屏、可视化 HTML 报告等证据，修 bug 要前后对比图，把人的验收成本降到最低；五、代码审查聚焦真问题，PR 尽量小，审查结果分级，人只盯 P0/P1 尤其安全和性能。245 赞、335 收藏。https://x.com/dotey/status/2124603209394078089
> [en] **Baoyu: when an agent says “verified,” how can you actually trust it?** Five lessons: 1) don’t rely on adversarial verification—agents critiquing each other without shared acceptance criteria often drift worse; 2) give clear criteria plus an environment to self-check, e.g. “screenshot the page and match the design pixel for pixel,” and it will build its own diff tool and redo the work; 3) verify early—feasibility, a prototype and a design doc before code; 4) make the agent hand over evidence such as screenshots, recordings, visual HTML reports and before/after shots for bug fixes, to cut your review cost; 5) focus code review on real problems—small PRs, graded findings, humans only checking P0/P1, especially security and performance. 245 likes, 335 bookmarks.
3. **卡兹克：我如何让 Claude、GPT 和 Gemini 协同干活**：他的判断是 Gemini 最好沟通、点子多但粗心、Harness 弱，Claude 审美和 Harness 最强但不够严谨，GPT 最严谨但最难沟通，所以让 Claude 站中间：大方案 Claude 出一份，再用自写的约 90 行脚本 agy-ask 让 Gemini 只拿原话和必要背景独立出一份再合并；界面文案和交互请 Gemini 当顾问；接口定死、与页面无关的成块后端、算法和数据处理用自定义脚本 codex-worker 派给固定 GPT-6.2 Astra xhigh，几十行的小改动 Claude 自己做；每个合并请求上线前必须过 GPT 审查，但只有算错钱、丢数据、越权、发错消息这类说得清触发路径的问题才挡上线。分工规则都写在 CLAUDE.md 里。https://x.com/Khazix0918/status/2124680457623425334
> [en] **Khazix: how I get Claude, GPT and Gemini to work together**: his read is that Gemini is the easiest to talk to and full of ideas but careless with a weak harness, Claude has the best taste and harness but isn’t rigorous enough, and GPT is the most rigorous but hardest to communicate with—so Claude sits in the middle. For big plans Claude drafts one while a ~90-line script, agy-ask, has Gemini draft another independently from his own words and minimal context, then Claude merges them; Gemini also consults on UI copy and interaction; self-contained backend, algorithm and data work with fixed interfaces goes to GPT-6.2 Astra xhigh through a custom codex-worker script, while Claude handles small edits itself; every merge request must pass GPT review before CI, but only issues with a clear trigger path—wrong money, lost data, privilege escalation, wrong messages—block release. The division-of-labor rules live in CLAUDE.md.
4. **Dex Horthy: a code-mode hack cut a daily Linear sweep from 245k tokens to 23k**: using Procedural Tool Calling (essentially code mode) in Factory, the job also dropped from 7 minutes to 36 seconds. In a separate thread he advises against blindly using a lab’s harness, but notes its tool definitions and system prompt are part of how the model was RL’d—own orchestration, backpressure, toolset, hooks and memory, but match the frontier harness on what’s core to the agent loop unless there’s a very strong counterargument. https://x.com/dexhorthy/status/2124624191563698426 https://x.com/dexhorthy/status/2124613833050472826
> [zh] **Dex Horthy：用 code mode 把每天的 Linear 巡检从 24.5 万 token 降到 2.3 万**：他在 Factory 里用 Procedural Tool Calling（本质上就是 code mode）实现，耗时也从 7 分钟降到 36 秒。另一条帖子里他建议别盲目照搬实验室的 Harness，但工具定义和系统提示词是模型 RL 训练的一部分：编排、背压、工具集、hook 和记忆可以自己掌控，Agent 循环的核心部分除非有很强的理由，否则尽量和前沿 Harness 保持一致。
