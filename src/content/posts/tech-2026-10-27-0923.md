## 新产品
1. **Hob: a free, MIT-licensed, on-device alternative to the Claude and ChatGPT desktop apps**: it works on your files like Claude Cowork but runs open-weight models (Gemma 4, gpt-oss) locally on Mac, Windows and Linux, auto-picks the best model for your hardware, writes sandboxed Python for ad hoc tools, and adds SearXNG web search, MCP connectors, image recognition and local file CRUD; chats and files never leave the machine and it works fully offline. ~112 points on Show HN; commenters said there are "a zillion of these" but upvoted anyway, and asked for a custom model directory and a native rather than Electron app. https://hob.chat [GitHub](https://github.com/FrigadeHQ/hob) [HN](https://news.ycombinator.com/item?id=50246238)
> [zh] **Hob：免费、MIT 许可、完全本地运行的 Claude / ChatGPT 桌面版替代品**：像 Claude Cowork 一样处理你的文件，但在 Mac、Windows、Linux 上本地跑开放权重模型（Gemma 4、gpt-oss），首次安装自动为你的硬件挑最合适的模型，能写沙箱化 Python 临时造工具，还有 SearXNG 网页搜索、MCP 连接器、图像识别和本地文件增删改查；对话和文件不出本机，可完全离线使用。Show HN 约 112 分；评论说「这类东西已经多如牛毛」但照样点赞，也有人想要自定义模型目录、希望做成原生应用而不是 Electron。
2. **Entire: a Git forge built for agent-human collaboration**: instead of the PR timeline, "Trails" puts agent-scored, customizable evals computed on every push at the top of the page; a new Git-compatible server claims pushes up to 89x faster than GitHub and 6x faster than Cursor Origin with multi-region replication; "Continuous Memory" syncs agent sessions and prompts into the repo (via git refs, per its field CTO) so agents can search them; CI partners are Buildkite and Depot. Available today. On HN one commenter agreed the PR stops being the right review unit when agents write the code, while others found the post too marketing-heavy and asked about pricing. https://entire.com/blog/the-git-forge-for-agent-human-collaboration [HN](https://news.ycombinator.com/item?id=50247453)
> [zh] **Entire：为「Agent 与人协作」打造的 Git 托管平台**：用「Trails」取代 PR 时间线，把每次推送后由 Agent 打分、可自定义的评测结果放在页面最上方；新的 Git 兼容服务器号称推送速度最高是 GitHub 的 89 倍、Cursor Origin 的 6 倍，并支持多地域复制；「Continuous Memory」把 Agent 会话和提示词同步进仓库（据其 Field CTO 说是用 git refs 实现），供 Agent 检索；CI 合作方为 Buildkite 和 Depot。今天起开放。HN 上有人认同「Agent 写代码后 PR 不再是合适的评审单位」，也有人嫌文章营销味太重、追问定价。

## 科技新闻
1. **Cloudflare: GLM-5.3 on Workers AI leaked other customers' data across requests — 155 responses affected**: from Aug 27 to Sep 9, prompts longer than 681,280 tokens could get answers containing data from other users' recent requests. The model was deployed with a 1,048,576-token context but the prefill KV cache pool only held 681,280 tokens; in SGLang's disaggregated prefill/decode mode an over-length prompt was swapped for a one-token placeholder instead of being rejected, so the decode node attended over stale cache pages. Reported by Gadi Evron (Knostic) via HackerOne, model pulled within 40 minutes of the incident and restored the same day with a larger pool and a patched engine; no evidence of deliberate exploitation, coordinated disclosure with SGLang. HN praised the RCA, and some wondered whether other providers would even notice such a bug. https://blog.cloudflare.com/kv-cache-exposure-remediation/ [HN](https://news.ycombinator.com/item?id=50252159)
> [zh] **Cloudflare：Workers AI 上的 GLM-5.3 出现跨请求数据泄露，共 155 条响应受影响**：8 月 27 日至 9 月 9 日，长度超过 681,280 token 的提示词，可能收到含有其他用户近期请求数据的回答。该模型按 1,048,576 token 上下文部署，但 prefill 端 KV 缓存池只能放 681,280 token；在 SGLang 的 prefill/decode 分离模式下，超长提示词没有被拒绝，而是被换成一个单 token 占位符，导致 decode 节点在残留的旧缓存页上生成回答。问题由 Knostic 的 Gadi Evron 通过 HackerOne 报告，Cloudflare 宣布事故后 40 分钟内下线模型，当天用更大的缓存池和修补后的引擎恢复服务；未发现蓄意利用，与 SGLang 协同披露。HN 称赞这份事故分析，也有人怀疑别的服务商根本不会察觉这种 bug。
2. **Ubicloud: vLLM's new constrained decoding takes tool-call schema accuracy from 92% to 100%**: serving Kimi K2.6 on vLLM 0.28, only 92% of tool calls matched the expected schema — 2 in every 25 failed, and agents then build on nonsense context; vLLM 0.31 exposes constrained decoding as a server-side flag that guarantees schema adherence for newer Kimi and DeepSeek models. The post walks through how tool declarations and calls are tokenized and parsed. An author is answering questions on HN, where one commenter wanted data on how constraining shifts output quality versus a back-off-and-retry approach. https://www.ubicloud.com/blog/fixing-tool-call-accuracy-in-vllm [HN](https://news.ycombinator.com/item?id=50242870)
> [zh] **Ubicloud：vLLM 新增的约束解码把工具调用 schema 准确率从 92% 提到 100%**：用 vLLM 0.28 部署 Kimi K2.6 时，只有 92% 的工具调用符合预期 schema——每 25 次就有 2 次失败，Agent 随后会在错误上下文上继续推理；vLLM 0.31 把约束解码做成服务端开关，可保证较新的 Kimi 和 DeepSeek 模型严格遵守 schema。文章还讲解了工具声明和调用如何被 token 化与解析。作者在 HN 答疑，有评论者希望看到约束解码对输出质量的影响，以及与「回退重试」方案的对比数据。
3. **Microsoft publishes the Type Server Protocol (TSP), a JSON-RPC protocol for querying a Python type server**: it answers protocol-version, snapshot, search-path, import-resolution and computed/declared/expected-type queries using LSP data shapes and a `typeServer/` method prefix, with TypeScript interfaces and a JSON schema as the source of truth; now at 0.4.1 with multi-connection negotiation. HN commenters said it should be called the Python Type Server Protocol, read it as a way to split Pylance from Pyright, and lamented it kept UTF-16 positions. https://github.com/microsoft/pylance-release/blob/main/docs/tsp/type-server-protocol.md [HN](https://news.ycombinator.com/item?id=50248371)
> [zh] **微软公布类型服务器协议 TSP：一种向 Python 类型服务器查询分析数据的 JSON-RPC 协议**：可查询协议版本、快照、搜索路径、导入解析，以及计算类型/声明类型/期望类型，沿用 LSP 的数据结构，方法前缀为 `typeServer/`，以 TypeScript 接口和 JSON schema 为权威定义；目前版本 0.4.1，新增多连接协商。HN 评论认为它应该叫「Python 类型服务器协议」，把它解读为让 Pylance 与 Pyright 解耦的手段，也有人遗憾它仍沿用 UTF-16 位置编码。
