## 新产品
1. **Claude Ship**: Anthropic’s new system for everything after a pull request is opened, in beta for Claude Team and Enterprise on GitHub. It combines three parts: Code Review (already GA, Quick/Standard/Deep levels per repo, findings adversarially verified before posting), PR Steward (beta; answers failing CI, merge conflicts and review comments, comments after every push with what it changed and how to undo it, and is designed never to approve or merge), and Claude Approvals (beta; applies an approval policy the team writes as a file in the repo, “like a smarter CODEOWNERS,” and Anthropic recommends starting in observe-only mode). Developers can type /ship in Claude Code to push, open the PR, review and fix it; admins can switch it on per repository with spend limits. Anthropic says merged PRs on the Claude Code team more than doubled from June to September while the share reverted fell over 40%. It is billed on tokens, is not available to ZDR, HIPAA or customer-managed-key orgs, and eligible Enterprise orgs can claim at least $10,000 in credits by Jan 15, 2027. The launch post on X had 17k likes; on HN one commenter traced the ladder from “Claude writes the code” to “Claude merges the code,” while another liked using a different vendor’s model to review code written with OpenAI models. https://claude.com/resources/articles/introducing-claude-ship https://x.com/ClaudeDevs/status/2124959436640858475 [HN](https://news.ycombinator.com/item?id=50618513)
> [zh] **Claude Ship**：Anthropic 针对「PR 开出之后」那一段推出的新系统，面向 GitHub 上的 Claude Team 和 Enterprise 用户公测。它由三部分组成：Code Review（已正式可用，每个仓库可选 Quick/Standard/Deep 三档，发现的问题先做对抗式核验再发评论）、PR Steward（公测，处理 CI 失败、合并冲突和评审意见，每次推送后说明改了什么、如何撤销，设计上绝不批准或合并）、Claude Approvals（公测，执行团队以文件形式写进仓库的审批策略，「像更聪明的 CODEOWNERS」，官方建议先用只观察模式）。开发者在 Claude Code 里输入 /ship 即可推送、开 PR、评审并修复；管理员可按仓库开启并设花费上限。Anthropic 称 Claude Code 团队 6 月到 9 月合并的 PR 增加了一倍多，被回滚的比例下降超过 40%。按 token 计费，不支持启用零数据保留、HIPAA 配置或客户自管密钥的组织；符合条件的 Enterprise 组织在 2027 年 1 月 15 日前可领取至少 1 万美元额度。X 上的发布帖有 1.7 万赞；HN 有人列出从「Claude 写代码」到「Claude 合并代码」的阶梯，也有人觉得用另一家的模型审 OpenAI 模型写的代码，正好职责分离。
2. **Shirudo**: an open-source Linux runtime from OpenAI and Cisco that lets defenders, with agents’ help, apply temporary “shields” to running systems while patches are tested and rolled out. Shields are eBPF programs that block the specific behavior a vulnerability needs while letting legitimate requests through; operators can watch a shield’s effect before enforcing it, shields are cryptographically signed and checked by the kernel’s eBPF verifier, and a TPM records what was loaded or removed. In a controlled test, a Codex-generated shield added an input check to Java’s Base64 decoder and blocked a Java4Shell exploit against a running Elasticsearch process without a restart. Licensed BSD-2-Clause (BPF programs dual BSD/GPL); OpenAI wants tested shields to ship alongside vulnerability disclosures. OpenAI’s post had 11k likes. https://shirudo.dev/ https://openai.com/index/introducing-shirudo/ https://github.com/shirudo-dev/shirudo [HN](https://news.ycombinator.com/item?id=50619630)
> [zh] **Shirudo**：OpenAI 与思科推出的开源 Linux 运行时，让防守方在 Agent 协助下，于补丁测试和上线期间给运行中的系统加上临时「护盾」。护盾是 eBPF 程序，只拦截漏洞利用所依赖的特定行为、放行正常请求；运维可以先观察护盾的影响再强制启用，护盾经过加密签名并由内核的 eBPF 校验器检查，TPM 记录加载和移除的过程。受控测试中，Codex 生成的护盾给 Java 的 Base64 解码器加了输入检查，在不重启的情况下挡住了针对运行中 Elasticsearch 的 Java4Shell 攻击。许可证为 BSD-2-Clause（BPF 程序为 BSD/GPL 双许可）；OpenAI 希望今后随漏洞披露一起提供测好的护盾。OpenAI 的发布帖有 1.1 万赞。

5. **Strands Decider v2**: AWS’s Strands Labs released five open decision models built on Gemma 4 (2B, E4B, 26B-A4B MoE and 31B dense, Apache 2.0), seven weeks after v1. A decision model doesn’t generate text: it takes a state such as a ticket or agent trace plus a question with fixed answers and returns a probability for each. The New Stack reports the 31B model averages 82.1 across six public benchmarks (Gemini Decision 1: 79.4) and cuts calibration error to 0.027 from 0.062, though it trails rivals on three of the six; v2 uses bidirectional attention so asking 20 questions about one trace costs little more than one. Inside Amazon, swapping Claude Sonnet 4.6 for the v1 E4B model on ticket labeling cut latency from 4,215 ms to 897 ms and list-price cost from about $22,200 to $500 per million tickets. Not yet on Bedrock. https://thenewstack.io/aws-strands-decider-v2/ https://github.com/strands-labs
> [zh] **Strands Decider v2**：AWS 的 Strands Labs 在 v1 之后七周发布五款基于 Gemma 4 的开放决策模型（2B、E4B、26B-A4B MoE、31B 稠密，Apache 2.0）。决策模型不生成文字：输入工单或 Agent 轨迹之类的状态，加上一个带固定选项的问题，返回每个选项的概率。The New Stack 报道，31B 版在六项公开基准上平均 82.1 分（Gemini Decision 1 为 79.4），校准误差从 0.062 降到 0.027，但六项中有三项落后对手；v2 改用双向注意力，对同一条轨迹问 20 个问题的成本和问一个差不多。亚马逊内部把工单打标从 Claude Sonnet 4.6 换成 v1 E4B 后，单次耗时从 4215 毫秒降到 897 毫秒，按标价每百万工单成本从约 2.22 万美元降到约 500 美元。目前尚未上架 Bedrock。

## 科技新闻
1. **Anthropic publishes a Claude-written proof that VP ≠ VNP over every field**: the anthropics/formal-math repo says circuits for the Hamiltonian cycle polynomial, and for the permanent outside characteristic 2, need more than m^(c (log m)^(1/3)) gates for all large m, also for approximating circuits; so VP is a proper subset of VNP and VNP is not in the closure of VP. The README stresses that this “does not settle P vs NP,” that the result was found by an internal research Claude model, and that the paper and its Lean 4 formalization were both written by AI with “no human mathematician” having checked the proof. Lean checks the proofs and CI re-checks them with a second, independently written kernel (nanoda), but no machine checks that Statement.lean says what is claimed. 271 points on HN; top comments asked what this means for math grad students, read it as a partial result on the way to P vs NP, and called releasing an unreviewed AI proof “either brave or stupid, or perhaps both.” https://github.com/anthropics/formal-math/tree/main/vp-vnp [HN](https://news.ycombinator.com/item?id=50620102)
> [zh] **Anthropic 公开一份由 Claude 写出的证明：在任意域上 VP ≠ VNP**：anthropics/formal-math 仓库称，对所有足够大的 m，计算哈密顿圈多项式的电路、以及特征不为 2 时计算积和式的电路，都需要超过 m^(c (log m)^(1/3)) 个门，近似电路同样如此；因此 VP 是 VNP 的真子集，且 VNP 不包含在 VP 的闭包中。README 特别说明这「并未解决 P vs NP」，结果由一个内部研究用 Claude 模型发现，论文和 Lean 4 形式化都由 AI 写成，「没有人类数学家」检查过证明。Lean 会检查证明，CI 还用另一个独立编写的内核（nanoda）复查，但没有机器能检查 Statement.lean 是否准确表达了所声称的命题。HN 271 分；热门评论有人问数学研究生该怎么办，有人认为这是冲击 P vs NP 途中的阶段性成果，也有人说未经人工审阅就发布 AI 证明「要么很勇敢，要么很蠢，也可能两者都是」。

2. **Founder Park 转载凯一的 Agent 评测半年复盘：评测是产品工程，抄一套 Harness 解决不了问题**：作者过去半年给 Tabbit Browser、Offloop 等通用 Agent 项目做评测，结论是模型评测只需定义问题，Agent 评测还要同时定义解决方案，Prompt、Tool、Skill 和 Harness 互相牵连，没法像模型团队那样把评测和迭代分开。他给出四条经验：先定评分指标再出题，不要一上来想题目；可观测性最重要，把产出截图、录屏、每步摘要、耗时、token、推理力度和加载的 Skill 都摊开给人看；敢下主观判断、直接上线做 AB 测试；对强时效任务一套快照做回归、一套从真实运行中提取维度。他还提醒，往 Prompt 里写「搜不够二十条就重试」能立刻刷高分，实际体验却未必更好。https://www.163.com/dy/article/LCESMVGC05566TJ2.html
> [en] **Founder Park reprints Kai Yi’s six-month retrospective on agent evals: evaluation is product engineering, and copying a harness won’t fix it**: after evaluating general-purpose agents such as Tabbit Browser and Offloop, the author argues that model evals only define the problem, while agent evals must also define the solution; prompts, tools, skills and the harness are entangled, so evaluation can’t be split off from iteration the way model teams do it. His four lessons: set the scoring criteria before writing tasks; treat observability as the most important part, laying out screenshots, recordings, per-step summaries, time, tokens, effort and loaded skills for people to judge; make subjective calls and ship A/B tests; and for time-sensitive tasks keep one snapshot set for regression and mine real runs for new dimensions. He warns that adding “retry until you have twenty results” to a prompt instantly lifts scores without necessarily improving the experience.
