## 有趣用法和干货
1. **Lauren Tan (poteto): how to automate anything with Grok Bot**: her long post argues automation is a learnable way of thinking with two parts, a goal and a process, and the common mistake is confusing a step (filling a form, sending an email) for the goal. Her method: tell a new bot the goal first, brain-dump your process by voice and have the bot restate it before doing anything, teach it the judgment you apply without thinking (which source wins when two disagree, what counts as done), give it ways to collect its own feedback such as reviews and logged data with consistent IDs, then trigger it with routines. The post drew about 8,000 likes and nearly 15,000 bookmarks. https://x.com/poteto/status/2123159537016533493
> [zh] **Lauren Tan（poteto）：用 Grok Bot 自动化任何事**：她的长文认为，自动化是一种可以学会的思维方式，由目标和流程两部分组成；常见错误是把流程里的一步（填表、发邮件）当成目标。她的做法是：先把目标告诉新建的 bot，再用语音把流程一股脑说给它听，并让它动手前先复述一遍；把你不假思索做出的判断也教给它（两个来源冲突信哪个、怎样才算做完）；让它能自己收集反馈，比如顾客评价，以及用统一 ID 串起来的记录数据；最后用 routine 让它自动触发。该文约 8000 赞、近 1.5 万收藏。
2. **OpenAI explains how the Codex sandbox works**: Michael Bolin’s post walks through Codex’s defaults: in a Git workspace it allows writes inside the workspace but keeps `.git` and `.codex` read-only (so it can’t touch `config.toml` or Git hooks), allows broad reads, and disables network access to block exfiltration. He is candid about the gaps: sensitive files elsewhere stay readable, and an agent could still plant code in an ignored `node_modules` package that your editor later runs outside the sandbox, which is why it relies on defense in depth. Permission profiles, a shared network proxy for domain rules, and a reusable `codex sandbox` command for your own tools are covered for macOS, Linux and Windows. https://openai.com/index/inside-the-codex-sandbox
> [zh] **OpenAI 讲解 Codex 沙箱的工作原理**：Michael Bolin 的文章拆解了 Codex 的默认设置：以 Git 仓库为工作区时，允许在工作区内写入，但 `.git` 和 `.codex` 保持只读（因此改不了 `config.toml` 和 Git hooks）；允许广泛读取；默认断网以防数据外传。他也坦白了漏洞：工作区外的敏感文件仍然可读，Agent 还可能把代码植入被 Git 忽略的 `node_modules` 包，之后被编辑器在沙箱外执行，所以要靠纵深防御。文中还介绍了权限配置、按域名放行的共享网络代理，以及可供自建工具复用的 `codex sandbox` 命令，并覆盖 macOS、Linux 和 Windows 的实现。
3. **Matt Pocock 对谈 Pi 两位作者：验证被高估了**：shao__meng 整理了这场约 46 分钟的直播。Mario Zechner 认为模型从 4.8 到 5.5 在系统设计、架构和 API 设计上没有大跃升，明显变好的是调度子 Agent 和一切能被测试验证的工作；他让 Agent 隔夜优化 Pi 启动时间，结果「降低了 100%」，因为模型几乎把模块全拆了。Matt 的概括是 Agent 擅长战术、不擅长战略；Armin Ronacher 补充，模型给的第一个方案「也算一种解」，但除非你告诉它正确的权衡，否则很少是更好的那个。Pi 的分诊机器人只有在问题已复现、现有代码让测试失败、修复让测试通过时，才让他们比较放心地合并。dexhorthy 转发的片段里，Mario 直言写了一堆 lint 规则和测试并不代表系统就好。https://x.com/shao__meng/status/2123220694444163503
> [en] **Matt Pocock with Pi’s two authors: verification is overrated**: shao__meng summarized the roughly 46-minute livestream. Mario Zechner sees no big jump from 4.8 to 5.5 in system design, architecture or API design; what clearly improved is orchestrating subagents and anything a test can verify. He once had an agent optimize Pi’s startup time overnight and got a “100% reduction” because the model had stripped out almost every module. Matt sums it up as agents being good at tactics, not strategy; Armin Ronacher adds that a model’s first answer is “a solution” but rarely the better one unless you tell it the right trade-offs. Pi’s triage bot is only trusted to merge when an issue is reproduced, existing code fails a test and the fix makes it pass. In a clip shared by dexhorthy, Mario says piles of lint rules and tests don’t mean the system is good.
